## 0. この文書の読み方

このプロジェクトは「市販リモコンで撃って人に付けた受光部で判定する」ところから始めて、最終的に「IDとダメージを載せた自作銃＋Wi-Fiスコアボード」まで伸ばす段階的な計画です。
いきなり全部作らず、**Phase 0 → 1 → ... と1段ずつ動くものを確認して進める**のが前提です。各フェーズの詳細は「6. 開発フェーズ」にあります。

用語:
- **銃 / 送信機**: 赤外線を出す側。
- **的 / 受信機 / 装着ユニット**: 人に付けて被弾を判定する側。
- **受光部 / 受光モジュール**: 38kHzの赤外線を復調してデジタル出力する部品（OSRB38C9AA等）。

---

## 1. 目的・コンセプト

家電リモコンと同じ **38kHz 変調赤外線** を使った、人に装着して遊ぶサバイバルゲーム用のレーザータグシステムを自作する。

### なぜ38kHzなのか
赤外線リモコンは「38kHz前後でON/OFFを刻んだ光」を送り、受光部がその38kHz成分だけを拾うことで、太陽光や照明のような“変調されていない光”を無視できる。これが裸のフォトダイオードではなく**復調つき受光モジュール**を使う理由。市販リモコンの大半が38kHz帯なので、銃を市販リモコンから始められる。

### 当たり判定を決めるのは何か（最重要）
当たり判定の大きさは **受光部のサイズではなく、相手に届いたときのビームの太さ** で決まる。
赤外線は広がりながら飛ぶので、受光部が直径5mmの点でも、ビームの円の中に受光部が入っていれば当たる。したがって「受光部を小さくしたら当たらなくなる」という心配は不要で、逆に**ビームを絞らないと誰にでも当たってゲームにならない**。詳細は「4. 機構設計」。

### 段階的なゴール
1. **MVP**: 市販リモコンで撃つ → 特定ボタンだけを被弾としてカウント → HPが0で「やられた」表示。
2. **拡張1**: 送信機も自作し、信号にプレイヤーID／チームID／ダメージ量を載せる。同士討ち無効。
3. **拡張2**: ESP32でWi-Fi接続し、被弾情報をスコアボードへ送信。

## 2. システム構成

```
┌─────────────┐        38kHz IR beam        ┌──────────────────────────┐
│  銃（送信機）  │ ─────────────────────────▶ │  的（受信機 / 装着ユニット）  │
│             │                            │                          │
│ 市販リモコン   │                            │ 受光部×4〜8（OUT並列）       │
│  or          │                            │  → マイコン (UNO/ESP32)    │
│ IR LED+MCU   │                            │  → HP管理 / 被弾演出         │
└─────────────┘                            └──────────────────────────┘
```

### 信号の流れ（受信側）
1. 複数の受光部の **OUTをすべて1本の入力ピンに並列接続**。受光部は通常時HIGH、信号受信中にLOWへ落ちる（オープンコレクタ的動作）。どれか1個が受ければピンがLOWになるので、配線本数に関係なくファームは同じコードで動く。
2. マイコンがIRremoteライブラリで信号をデコードし、Protocol / Address / Command を得る。
3. 自分を倒せる弾の定義と一致したら被弾処理（HP減算・無敵時間・演出）。

> なぜOUTを並列にしてよいのか: 受光モジュールのOUTは「信号が来たらLOWに引く」出力で、アイドル時は内部プルアップでHIGH。複数を束ねても、どれか1つがLOWに引けば全体がLOWになる（ワイヤードOR）。マイコン側は `INPUT_PULLUP` でなくIRremote標準の入力でよいが、長い配線ではプルアップ強化を検討。

> ⚠️ 間違えて買わない部品
> - **TSSP77038系**: 近接センサ／光電スイッチ向け。リモコンコード判定には使えない。
> - **TSMP96000系**: 38kHzフィルタなしのコード学習向け。今回は不要。

### 3.2 受光部のピン配置（OSRB38C9AA）
- 1番: OUT → マイコンの D2
- 2番: GND
- 3番: VCC
- ※ 品番ごとに並び順が違う。VS1838B等は並びが異なることが多いので、**必ず各データシートで確認**してから配線する。逆接続すると壊れる。

### 3.3 配線（素の受光部で組む場合・1個分）
```
VCC(5V) ──┬── 100Ω ──┬── 受光部 VCC(3番)
          │          │
          │        10µF  (受光部のVCC-GND間に、部品の近くで入れる / +極をVCC側)
          │          │
GND ──────┴──────────┴── 受光部 GND(2番)

受光部 OUT(1番) ── (他の受光部OUTと並列に束ねる) ── マイコン D2
```
- 100Ω＋10µFは**受光部ごとに**付ける。配線が1m程度に伸びても誤動作しにくくなる（モーターやLEDの突入電流によるノイズ対策）。
- 基板付きモジュール（VS1838Bモジュール等）は抵抗・コンデンサ実装済みのものが多く、そのまま3本挿しでよい。

### 3.4 振動モーター／ブザーの駆動
マイコンのピンから直接モーターを回さない（電流不足・逆起電力でピンが壊れる）。トランジスタで駆動する:
```
マイコンの VIBE_PIN ── 1kΩ ──┤ベース
                               │(NPN 2N2222)
電源(5V) ──[振動モーター]── コレクタ
                               │
                          エミッタ ── GND

モーターと並列に逆向きのダイオード(1N4148/1N4007)を入れる(フライホイール)
```
- **ブザーは自励式（アクティブ）を使う。** Uno/Nanoでは `tone()` がIRremoteと同じタイマーを奪い、受信が壊れるため、トーン生成が不要なアクティブブザーにする。
- 屋外では音が聞こえにくいので、**振動モーター＋高輝度LED** を被弾フィードバックの主役にする。LEDが光ると周囲にも「やられた」が見える。

### 3.5 電源・消費電流のざっくり見積り
| 負荷 | 目安電流 |
|------|---------|
| Arduino UNO | 約50mA |
| 受光部 ×8 | 各1〜5mA → 約40mA |
| LED（点灯時） | 約20mA |
| 振動モーター（動作時） | 約80〜100mA |
| 合計（被弾演出中のピーク） | 約210mA |

5Vモバイルバッテリー（2000mAh）なら理論上10時間級。実運用では十分。ESP32でWi-Fiを使う場合は送信時にピーク数百mAが乗るので、容量に余裕を持たせる。

## 4. 機構設計（当たり判定のチューニング）

### 4.1 ビーム太さの計算
ビーム直径の目安 ≒ `2 × 距離 × tan(広がり半角)`

| 銃の状態 | 5m先 | 10m先 | 20m先 |
|----------|------|-------|-------|
| 生のリモコン（±15°前後） | 約2.7m | 約5.4m | — |
| 黒い筒で絞る（±3°） | 約50cm | 約1m | 約2m |
| レンズで絞る（±1°） | 約17cm | 約35cm | 約70cm |

- 胴体幅が約40cmなので、サバゲーとして面白いのは **±1°前後（レンズ使用）**。
- 生のリモコンは「だいたいあっちに向ければ当たる」ので、そのままではゲームにならない。

### 4.2 銃側の絞り方
- 先端に**黒い筒（10〜15cm）**をかぶせて周辺光を切り、直進成分だけ通す。
- さらに**100均ルーペ（凸レンズ）**をIR LED（リモコンの発光部）から焦点距離に置くと、光が平行に近づきビームが細く・遠くまで届く。レンズ位置は実測で前後に動かして一番遠くの的に当たる位置に調整。
- ドットサイト代わりに筒の上に簡単な照準（針金のピープサイト）を付けると狙いやすい。

### 4.3 受光側の絞りと遮光
- 受光部を**短い黒筒／フード**に入れ、正面からの光だけ受ける（反射・横からの誤爆を減らす）。
- 屋外では**上からの太陽光を遮るひさし**を各受光部に付けるのが必須。直射下では受光部が飽和して感度・距離が大きく落ちる。

### 4.4 体への装着
- 受光部1個の受光範囲は正面±45°程度。全方向で撃たれても判定するには複数配置する:
  - **頭**: ヘッドバンドに前後左右の4個
  - **胴**: 胸・背中・両肩
- 近距離ではビームが細くなるので、**受光部どうしの間隔を20〜30cm**にして「胴の真ん中を狙えばどれかに入る」密度にする。狙って当たらない問題（近距離でビームが受光部の隙間を抜ける）を防げる。
- 配線は可動部（肩・首）で断線しやすいので、より線＋結束＋コネクタで分離できるようにしておくとメンテしやすい。

## 5. ファームウェア設計

### 5.1 MVP（市販リモコン受信）の動作フロー
1. IRremoteで受信し、`Protocol / Address / Command` をシリアル(115200)に表示。
2. 自分の銃ボタンの値を `GUN_PROTOCOL / GUN_ADDRESS / GUN_COMMAND` に書き込む。**TODO: Phase 0で使う市販リモコンの型番と、対象ボタンの実測値をここに記入する**（NEC以外のプロトコルの可能性あり）。
3. 受信コードが一致したら被弾 → HP減算。
4. 被弾後は **無敵時間（3秒・ゲームルールで調整）** を設け、1発で多重ヒットしないようにする。
5. 長押しのリピート信号（NECのリピートフレーム）は無視 → ボタン連打＝連射。
6. HP=0で「やられた」演出（LED点灯維持＋振動）。以降は受けない or リスポーン待ち。

### 5.2 状態遷移（概念）
```
[ALIVE] --被弾(HP>0)--> [ALIVE] (HP--, 無敵3000ms, 演出150ms)
[ALIVE] --被弾(HP=0)--> [DEAD]  (LED点灯維持)
[DEAD]  --リスポーン操作--> [ALIVE] (HP=MAX)   ※将来: ボタン or 管理者信号
```

### 5.3 将来の信号フォーマット（送信機自作時）
NEC方式は Address(16bit) ＋ Command(8bit) を運べる。意味を割り当てる例:

| フィールド | ビット | 意味 |
|-----------|--------|------|
| Address[15:13] | 3bit | チームID（最大8チーム） |
| Address[12:8]  | 5bit | プレイヤーID（最大32人） |
| Address[7:0]   | 8bit | （予備 / マジックナンバーで自作弾の識別） |
| Command[7:4]   | 4bit | 武器種別（ダメージテーブル参照） |
| Command[3:0]   | 4bit | ダメージ量 or チェックサム |

- 受信側で「**自チームからの弾は無効（同士討ち防止）**」を実装。
- マジックナンバーで「このゲームの弾」かを判定し、他人の家電リモコンの誤爆を弾く。
- 連射レートや弾数（リロード）はファームで制限するとゲーム性が出る。

### 5.4 調整パラメータ
| 項目 | 初期値 | メモ |
|------|--------|------|
| MAX_HP | 5 | ゲームバランス |
| INVINCIBLE_MS | 3000 | ゲーム上の無敵時間（運用マニュアルと同値）。1発の多重ヒット防止も兼ねる |
| HIT_FEEDBACK_MS | 150 | LED/振動の点灯時間 |
| IR_PIN | D2 | 受光部OUT並列接続 |
| HIT_LED | D5 | 被弾LED |
| VIBE_PIN | D6 | 振動モーター（トランジスタ駆動） |

実装は `arc/ir_rx_test.ino` を参照。

## 7. リスク・注意点とトラブルシュート

| 症状 / リスク | 原因 | 対策 |
|---------------|------|------|
| 昼の屋外で届かない/鈍い | 直射日光で受光部が飽和 | 受光部にひさし、まず屋内/夕方で運用、Phase5で強力LED |
| 向けてないのに当たる | 生リモコンのビームが広い/壁反射 | 銃に筒＋レンズ、受光側にフード |
| 1発で何発も減る | 多重ヒット | 無敵時間 INVINCIBLE_MS を調整 |
| 連射できない/勝手に連射 | リピートフレームの扱い | リピートは無視（連打＝連射）に設定済み |
| 受信が時々壊れる | `tone()` とIRremoteのタイマー競合 | アクティブブザー採用、またはESP32/別タイマー |
| 受光部が反応しない/発熱 | VCC/GND/OUT逆接続 | データシートでピン順を確認（品番ごとに違う） |
| モーター動作時に誤受信 | 電源ノイズ・逆起電力 | 受光部ごとに100Ω＋10µF、モーターにフライホイールダイオード |
| 近距離で狙って当たらない | ビームが受光部の隙間を抜ける | 受光部間隔を20〜30cmに密に配置 |

## 付録A. UNO直結での最小動作確認（旧メモ修正版）

> ここにあったメモは外部生成のレポートの転載で、**48kHzモジュール前提・保護回路全般を不要とする記述**があり本文と矛盾していたため、38kHz・本設計の方針に合わせて修正して残す。
> この付録は **Phase 0の疎通確認用の最小構成** を示すもので、ゲームの被弾判定は5章のIRremoteデコードを使う。

### A.1 直結してよい範囲（UNO / ATmega328P）

| 接続 | 直結可否 | 条件 |
|------|----------|------|
| 受信モジュール OUT → D2 | OK | 出力はロジックレベル。3.3の100Ω+10µFは付けておくと安定 |
| アクティブブザー → D8 | 条件付きOK | **5V駆動・消費電流20mA以下の圧電アクティブブザー**のみ。電磁式・大音量タイプはNG |
| 振動モーター | **NG** | 3.4の通りトランジスタ＋フライホイールダイオード必須 |
| 送信IR LED（高出力） | **NG** | 数十〜100mA流すので3章のトランジスタ駆動必須 |

### A.2 この最小構成の限界

`digitalRead`でOUTのLOWを見るだけの構成は「**何かIRが来たら鳴る検知器**」であり、誰の・どのボタンの信号かは判別できない（照明ノイズや他人のリモコンでも鳴る）。あくまで配線と受光部の生死確認用。ゲームでは必ずIRremoteでデコードして `GUN_*` 一致で判定する。

### A.3 ノンブロッキング最小コード（疎通確認用）

```cpp
const int SENSOR_PIN = 2; // 受信モジュール OUT (アクティブLow)
const int BUZZER_PIN = 8; // アクティブブザー(+)  ※tone()は使わない

bool isBuzzerActive = false;
unsigned long buzzerStartTime = 0;
const unsigned long BUZZER_DURATION = 500; // 疎通確認用は0.5秒で十分

void setup() {
    pinMode(SENSOR_PIN, INPUT);
    pinMode(BUZZER_PIN, OUTPUT);
    digitalWrite(BUZZER_PIN, LOW);
}

void loop() {
    unsigned long currentMillis = millis();
    int sensorState = digitalRead(SENSOR_PIN);

    if (sensorState == LOW && !isBuzzerActive) {
        digitalWrite(BUZZER_PIN, HIGH);
        isBuzzerActive = true;
        buzzerStartTime = currentMillis;
    }
    if (isBuzzerActive && currentMillis - buzzerStartTime >= BUZZER_DURATION) {
        digitalWrite(BUZZER_PIN, LOW);
        isBuzzerActive = false;
    }
}
```

- `delay()`を使わず`millis()`差分で管理するのは正しい方針（鳴動中も他の処理をブロックしない）。この考え方は5章の本実装でも使う。
- `currentMillis - buzzerStartTime` の減算形式は `millis()` のオーバーフロー（約49.7日）でも破綻しない。
- `tone()`は**使わない**：UnoではIRremoteと同じタイマー（Timer2）を奪い受信が壊れる（3.4参照）。アクティブブザーは`digitalWrite`で鳴らす。
